结论

给 Hyperloom 一个推理服务和加速目标，它会先测出起点，再一轮轮试改动。每一轮都要回答为什么改这里、这次改动值不值得留，以及下次从哪个版本继续。

压测、Profile、SWEEP 各在什么时候跑？

一轮候选试跑用 Benchmark Runner 测成绩。Profile 另开任务采设备证据。退出优化阶段后，SWEEP 在多个并发档比较基线启动配置和当前整套配置。同一个框架阶段可以试多项候选，共用一份热点报告。

  • 第一次。 PRELUDE 拿到有效基线后，如果环境支持抓设备 Trace，准备预算足够，且预热回放等任务已让出资源，Coordinator 登记采集任务。Dispatcher 按资源启动它。
  • 优化途中。 一次改动通过端到端验证后，如果当前吞吐比上次采集对应的成绩高至少 10%，且没有采集任务在途，Coordinator 可尝试排复采。算子入口发现配置或负载变了、SWEEP 回到框架阶段等情况，也有自己的复采检查。

采集任务启动以后，Profiler 再跑一趟请求，在选定的请求窗口记录设备活动。如果任务叫 Roofline，拿到可用 Trace 后，同一个任务就调用 Trace Analysis 汇总热点。只安排 Profile 时，先得到 Trace，可以再单独安排分析。

沿着 100 → 110 → 112 → 110 走一遍

  1. 起跑。 Runner 测出原始版 100。本例具备采集条件，PRELUDE 另排一次 Roofline，采集并分析 100 版的时间线。
  2. 调参。 Explore 调 Runner 测出 110，通过后记为当前版。如果上次采集的吞吐锚点是 100，这次达到 10% 的刷新线。采集任务获准运行后，用 110 版重新找热点。
  3. 试算子。 Integrate Patch 用 Runner 测出 112。示例中收益低于门槛，Session 记录 112 和回退原因，下一回合继续从 110 出发。这次普通压测已经足以形成性能结论，无须因此给 112 再拍一份时间线。
  4. 扫描。 进入实际 SWEEP 时，用基线启动配置和 110 对应的已接受配置跑成对档位。100 和 110 是固定工作点的旧读数，各档会重新计时。两层都改时，Runner 同样启动整套 SGLang 服务。查看整栈怎么测。

Coordinator 用最新共享状态和新消息组装下一次 Orchestration 的输入。Session 的 state.json 保存当前版、成绩和分析摘要等状态；查原始请求、日志或设备事件时，再沿产物路径打开对应任务目录。

框架参数怎么改

如果长提示拖慢正在生成的短请求，可以把 Prefill 分块上限（chunked-prefill-size）从 4096 调到 2048 作对照。只替换这一个启动值，固定模型、请求、并发和其余配置。看输出吞吐、首词延迟 TTFT、词间耗时 TPOT，以及输出质量。在本教学例里，候选通过后才把这组参数保存为 110 版。

框架源码补丁怎么改

先定位框架的后端分发点。以 SGLang PR #41071 为例，只在指定设备、FP8 路径和显式开关命中时调用另一套 GEMM。先核实新分支确实命中，再比较端到端吞吐和质量。真实 PR 在吞吐改善而准确率回落后，最终保留为可选方案。

谁收到 Forge 的 REVERT？

在 1.1.5 的 Forge 入口路径里，补丁集成是算子阶段任务内部的一步。单个补丁的 REVERT 进该任务的集成汇总。任务将完整结果落盘，并向 Orchestration 的收件箱发摘要。Dispatcher 回收的是整项任务完成或失败的状态，并登记结束、归还资源；这个状态与单个补丁的去留是两层结果。

谁给 Orchestration 输入？为什么算子入口由 Coordinator 启动？

Coordinator 在主循环里发起获准的 Agent 回合，把目标、阶段、预算、当前版、热点和收件箱整理成上下文。Orchestration 据此提参数、委托源码任务，或建议转向算子。Dispatcher 收回的结果经结算进入共享状态和消息。Session 供留档和恢复。

编排回合每次读最新可用的状态。基线建立、已验证收益跨过刷新阈值、或 SWEEP 回到新一整轮等时机可以请求刷新分析。同一份热点在刷新完成前可用于多个编排回合。

建议由 Router 记录，实际切换看阶段规则。进入算子阶段时，Coordinator 通过阶段入口登记内部任务，Dispatcher 启动它。在算子阶段，Orchestration 仍可申请候选分析或集成，后端的自动启动由程序入口负责。

一项候选结束，还是一整轮结束？

框架阶段同时跟踪参数和源码两条路线。比如 110 被接受后，源码还有可试方向，Coordinator 可以留在框架阶段继续。两条路线都停滞、阶段预算耗尽，或有效推进建议被阶段规则采纳时，才准备退出框架阶段。

ConcSweepExecutor 返回扫描状态和摘要。Dispatcher 回收后由 Coordinator Writeback 写入 last_conc_sweep。Phase Machine 读该状态、预算和收敛条件，决定回框架或收尾。回框架时，从当前接受版 110 继续。查看结果怎样回传。

框架和算子都改了，谁测最终组合？

两层改动都 KEEP 时，Coordinator 的写回把它们放进优化栈。current_best 对应一套可以启动的 SGLang 组合，包含接受的框架改动、参数和有效的算子产物。

  1. 算子候选集成器用带框架已接受改动的版本加载候选算子，然后测整个服务。因此算子候选的 E2E 已包含当前框架Benchmark Runner
  2. Benchmark Runner回整套服务成绩。集成器据实测结算，实际提交后的 KEEP 调用 Coordinator Writeback。算子候选集成器
  3. Coordinator Writeback按实测和加载证据入账。区分已接受的组合与累计成绩已验证到哪一代SharedState
  4. SWEEP 入口先恢复中断的栈验证，收齐待集成 KEEP，并按条件验证可组合的正收益候选，再准备扫描KernelStack
  5. CLOSE如果最终还有未验证的 KEEP，而且基线、预算和资源允许，请求排整栈复测。Coordinator Writeback
  6. Coordinator Writeback登记内部 stack_revalidate。Dispatcher 启动单候选 Explore，Explore 调 Benchmark Runner 测当前整套配置。Dispatcher
  7. Benchmark Runner实测回 Explore。Dispatcher 回收后，Writeback 用整栈成绩更新对原始基线的累计收益。Explore → Dispatcher → Writeback
  8. Coordinator 与 Report记录整栈已复测、失败或为何跳过，报告链接最终版本和实测依据Session
Benchmark Runner 测的是整套 SGLang 服务

Forge 内部计时只能说明算子自身耗时。整栈验证看同一套服务内框架加算子的实际运行。已验证的整栈无需在 CLOSE 再补同一趟。 例如另有一个算子候选在框架 110 的基础上通过验收，服务实测 115。实际启动的是框架加算子的组合，对原始 100 的累计收益为 15%。这里的数字仍是教学设定。

SWEEP · 谁扫描，扫完谁决定继续？

框架阶段退出且算子关闭时直接来到此入口。算子开启时先退出算子阶段。这里扫描的是两套启动配置在不同并发下的服务成绩。

  1. SWEEP 阶段入口检查扫描开关、上次扫描后有无新增验证收益和预算，获准后登记 conc_sweep。跳过时写终态和原因Dispatcher
  2. Dispatcher派发扫描任务。Executor 从共享状态读基线启动配置和当前接受的整套优化配置ConcSweepExecutor
  3. ConcSweepExecutor逐档调用 run_grid。基线臂先跑，优化臂复跑基线臂到达的档位。两边都完成的档位才成对比较Benchmark Runner
  4. ConcSweepExecutor交状态、配对数、摘要和结果文件。Dispatcher 回收并广播结果，Writeback 更新 last_conc_sweepDispatcher → Coordinator Writeback
  5. Phase Machine下一次阶段判断读扫描终态、目标、预算和收敛条件。扫描失败进入 CLOSE，其余按条件决定能否回框架框架阶段或 CLOSE
  6. CLOSE必要时做最后的整栈复测，再汇总已验证收益、扫描和停止原因，保存证据与可复用经验Report 与 RecipeKB
看 SWEEP 结果时核对两边实际加载了什么

这条源码路径明确重建的是两套启动配置，优化臂也可加载已接受 overlay。它对扫描设置 RUN_EVAL=false。做严格的原始源码整栈对照时，还要核对两臂实际加载的源码提交和构建产物。

下面用一场教学实验贯穿每张卡。原始成绩为 100 token/s。第一轮调参后接受 110，第二轮算子候选在相同请求下测到 112。小图从左到右表示接到什么、做了什么、交给谁。

状态与消息→推进主循环→编排回合／Dispatcher

阶段规则看待办、预算等条件。进入算子阶段时，Coordinator 登记内部任务，再由 Dispatcher 派发。

看一次真实的取舍 · 吞吐翻倍，为什么还要留开关？

Hyperloom 在优化另一个模型时发现了候选路径。SGLang PR 的作者随后人工审查并实测，下面取其中 Qwen3-32B-FP8 在 MI300X 上的数据。3

指标Triton → CK
输出吞吐 · 并发 442 → 173 token/s，输入 1024，输出 512
输出吞吐 · 并发 128225 → 337 token/s，输入 8192，输出 1024
GSM8K 平均准确率83.2% → 80.9%，各测三次

最终合并为主动开启的选项。 请求形态变化后，速度收益也变了。准确率回落支撑了保留原默认路径的决定。3

迁到双卡 910B · 第一轮交什么证据？

免费单卡先演练 SGLang 启动、固定请求、输出校验和 trace 导出。到了双卡，单独建立一份原始基线，同步采两 rank 的 Profile，再把候选放回同一双卡环境做端到端对照。

比如一张卡先进入集合通信，另一张还在算。把两条时间线按同一步对齐，再判断时间花在等另一张卡，还是花在真正传输。这个判断会改变下一轮该调查计算、调度还是通信路径。

首版保留协调、独立验证和结果留档。服务启动、Profiler、设备同步和算子构建按昇腾平台接入。这个项目的双卡并行方式与模型仍待锁定。
