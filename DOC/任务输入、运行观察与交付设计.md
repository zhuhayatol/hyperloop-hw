# Hyperloop 任务输入、运行观察与交付设计

人写任务，决定评测标准和可改范围。启动后，由 Hyperloop 自己完成采集、Agent 调用、执行、测量和留证，支持无人值守运行。人可以在运行中查看进度、暂停派发或给出新的调查方向。结束后，另一个人只凭这次运行保存的文件也能复核结论。

单命令启动、终端交接日志、运行摘要和主负载双指标验收已接入源码。运行中人工暂停和改向、独立留出请求复测仍是设计项。下面沿用同一个 910B3 任务，时间、候选编号、消息、成绩和产物路径均为设计样例。 [当前运行与复核方式](运行与复核.md) · [已有真机验证](910B3闭环补验.md)

## 1. 填两个文件，用一条命令启动

用户准备 `任务.md` 和 `启动配置.yaml`，然后在终端执行同一条 `start` 命令。换目标时改任务文件，换设备、负载或预算时改启动配置。

### 文件一 · 任务.md

写清楚优化对象、对照版本、要调查的方向和验收指标。下面是本例的任务文件。

```markdown
# 改善 910B3 上的 SGLang 推理性能

使用项目现有的 910B3 单卡环境和 Qwen2.5-0.5B-Instruct BF16。
以原始分块 512 的服务为基线，保留当前固定的 Prefill 和 Decode 请求。
调参、框架补丁、算子三个方向都要有调查结论。根据 Profile 决定先查哪里。

最终在同一个版本上，相对原始基线把吞吐提高至少 15%，
把首 token 延迟（TTFT P95）降低至少 15%。
模型输出逐 token 一致，后续 token 延迟（TPOT P95）最多增加 10%。
预算用完时，交付最后一个有完整证据的接受版，并列出还差哪些目标。
```

### 文件二 · 启动配置.yaml

至少填 `target`，本例选 `910b3-tp1`。它带入现有的卡、SGLang、模型、固定请求集和默认运行参数。其他字段按需填写，项目用它们覆盖预设，并在终端显示最终采用的值。任务文件路径在启动命令中指定。

```yaml
target: 910b3-tp1
session_id: demo-910b3-01
session_root: .runs
baseline_mode: measure

workload:
  concurrency: 2
rules:
  warmup: 2
  repeats: 3

settings:
  max_cycles: 3
  max_turns_per_cycle: 2
  budget: 45
  profile_enabled: true
  sweep_enabled: true
  sweep_concurrency: [1, 2, 4]
  kernel_backend: forge

agent_provider: deepseek
```

示例中，`workload.concurrency` 是正式验收并发，`sweep_concurrency` 是额外扫描的并发点。`rules.warmup` 和 `rules.repeats` 分别控制预热和正式测速轮数。`max_cycles` 限制优化循环数，`budget` 按预计任务开销扣减。会话名可以自动生成，`session_root` 决定结果存放位置。DeepSeek 凭据和 SGLang 底层启动参数沿用项目已有的环境设置。

`baseline_mode` 默认是 `measure`。需要跳过启动时的原版基线测量时，将这个顶层字段设为 `reuse_latest`。项目在 `session_root` 下按原始基线实际测量时间选择最新的兼容记录，匹配运行模式、目标与实际运行时、原版 SGLang 执行栈、模型与 tokenizer、完整负载及测量和评估规则，并核验证据。没有匹配记录时会停止并说明原因。设为 `measure` 后重新启动可建立新基线。

### 在终端输哪一条

在已配置好 Hyperloop 的终端中，从这两个文件所在的目录执行。文件放在其他位置时，两个选项也可以使用绝对路径。

```bash
python -m hyperloop start --task "任务.md" --config "启动配置.yaml"
```

执行后，项目依次完成以下操作。

1. **读取任务并锁定条件。** 核对设备、版本、负载、基线和验收标准，把任务原文及实际生效的设置写入本次记录，并在终端给出摘要。关键条件冲突或有歧义时，指出需要修改的文件和字段。
2. **准备 Reference 和原始基线。** `measure` 模式在真机独立采集原版 Reference 并建立基线。`reuse_latest` 沿用已验证的原始基线及其真机 Reference。准备失败时显示原因和日志位置。
3. **开始优化。** 启用 Profile 后，若复用了基线，就优先使用同一来源验证通过的 Profile。无可用 Profile 时现场采集。Agent 随后根据已确认的热点提案。候选配对测试与最终验收配对复测均在本轮执行，终端打印会话目录和日志、信号流、Markdown 报告的入口。

本例显示 `512` 为原始基线，历史 `768` 是需要重测的线索。项目把用户目标转换成可核对的条件，随实际负载和基线一起冻结。单轮保留候选要相对配对父版达到 5% 吞吐收益，并通过正确性和延迟限制。最终验收读取独立复测回执，要求**同一个实际加载的候选**在同一工作点上同时满足以下条件。

- 吞吐至少达到原始基线的 `1.15` 倍。
- TTFT P95 至多为原始基线的 `0.85` 倍。
- 输出逐 token 一致，TPOT P95 在锁定的回归门槛内。

每项检查分别保存数值、结论和证据。只有全部条件通过，项目才登记本任务达标。会话因预算或其他原因结束时，仍交付最后一个有完整证据的接受版，并标出尚未通过或尚未测齐的项目。

`start --task --config` 是项目的统一入口。可以从仓库的 Markdown 任务示例和 YAML 启动配置开始。 [入口与真机用法](运行与复核.md) · [Markdown 任务示例](../configs/task.910b3.optimization.md) · [YAML 启动配置](../configs/start.910b3.protected.yaml)

## 2. 运行中怎么看每个 Agent 的交接

交接由 Hyperloop 在实际运行时记录。角色调用保存项目发给 Agent 的输入和收到的回复，发出方登记消息与接收方，接收部件保存自己实际做了什么。消息、处理结果和任务编号可以互相对照。缺少返回回执时，记录显示仍在等待或调用失败。

终端日志用短句说明**当前哪个部件在做什么、正在等什么、完成后得到什么**。这些句子由项目按事件字段生成，同时写入会话的 `console.log`。动态信号流图读取同一份会话事件，在箭头上显示交接内容，点击可展开实际回复、处理回执和证据。例如本轮的终端日志会有下面两条。

```text
10:47 · #94 · Dispatcher 已把整栈候选 R04 交给 Evaluator 复测。
10:47 · #95 · Evaluator 正在核对 SGLang 是否同时加载框架补丁和新算子。
```

下面是一轮不完整的运行摘录，用同一任务展示调参、换向、框架补丁和算子的交接。

| 时间／事件 | 发送方 → 接收方 | 发了什么 | 对方怎么处理 |
| --- | --- | --- | --- |
| 09:10／#12 | Profiler → Coordinator | 原版的 Prefill、Decode 采集摘要和 trace 位置。 | 把热点与冻结工作点绑在一起，交给本轮提案使用。 |
| 09:11／#14 | Coordinator → Orchestration | 交任务、原版 `512`、热点摘要、历史 `768` 和剩余预算。 | 选一个能检验当前假设的尝试。 |
| 09:12／#17 | Orchestration → Intent Router | 「先用同一请求对照分块 `512` 和 `768`，看减少分块次数能否缩短 Prefill。」 | 核对参数和阶段，登记调参候选 `R01`。Dispatcher 获得资源后把两个规格交给 Explore。 |
| 09:24／#29 | Evaluator → Coordinator | `R01` 四组输出一致。配对吞吐提高 3%，低于本例冻结的单轮接受线 5%。 | 按独立裁决 `REVERT` 归档，当前版继续使用原版。 |
| 09:41／#43 | Evaluator → Coordinator | `R02` 分块 `640`，配对吞吐提高 1.2%，在本例测量波动范围内。 | 保留原始样本并回退。 |
| 09:43／#46 | Coordinator → Orchestration | `R01` 和随后尝试的 `R02` 都改变分块，仍无达到门槛的收益。现有采集分不清排队、框架准备和设备 Prefill。 | 暂停继续枚举分块，先请求分段证据。补测结果返回后调查框架。 |
| 09:56／#52 | Trace Analyzer → Coordinator | 同一请求的时序显示，主要额外时间发生在出队后、送入设备前，trace 中重复出现输入准备调用。 | 保存对应时序和调用证据，在下一回合交给 Orchestration。 |
| 09:58／#56 | Orchestration → Intent Router | 「慢请求在进入设备前有重复准备工作，请 Specialist 定位调用点和检查能否复用。」 | 核准专项调查，Dispatcher 把工作点、热点和允许的文件范围派给 Specialist。 |
| 10:07／#62 | Specialist → Intent Router | 「提议复用同一请求已经准备好的输入描述，省掉调度路径上的重复构造。」附 `R03` 补丁、适用条件和测试办法。 | 登记正式提案。Coordinator 把补丁和证据送入 Critic 的审查回合。 |
| 10:09／#65 | Critic → Intent Router | 「可以试跑。请覆盖不同输入长度，核对是否会错误复用上一请求的数据。」 | 将审查意见回给提案方，登记隔离集成任务。Dispatcher 派发后，执行端才构建并启动候选。 |
| 10:31／#78 | Evaluator → Coordinator | `R03` 输出一致，吞吐从 100.00 到 109.00 tok/s，TTFT P95 从 200.00 到 174.00 ms，TPOT 在门槛内。 | 保存 `KEEP`、证据和补丁，后续候选从 `R03` 起步。双指标总目标仍待验证。 |
| 10:42／#86 | Coordinator／Kernel Agent → Forge | 交 `R03` 的实际热点、目标算子和可测形状。 | Forge 构建候选、做独立数值校验和设备计时，把新算子补丁和调用证据交回。 |
| 10:47／#94 | Dispatcher → Evaluator | 交包含 `R03` 框架补丁与新算子的整栈候选 `R04`。 | 在隔离 SGLang 进程核对两处改动确实加载，逐 token 校验后再测整套服务。 |

每个 Agent 的提案、审查意见、退回和失败都应能查到对应记录。Agent 的预测标作「提案」，测试结果和版本裁决按独立回执显示。运行时的日志、交接和实测记录由项目自动生成和保存，随运行推进就可以查看。

## 3. 卡住了，项目怎么换方向

### 项目自己发现

Coordinator 按「想解决什么问题、改的是什么、得到什么新证据」记录尝试。`R01` 用 `768`，`R02` 用 `640`，都在尝试用分块大小减少 Prefill 开销，归在同一个方向。重跑一次以确认波动可以有价值，日志说明这是复测及其理由。

本例里，两次尝试都缺少达到门槛的收益，已有数据也解释不了慢请求为什么慢。Coordinator 把已试的方向、证据缺口和剩余预算交给 Orchestration。Orchestration 先给出可以区分的解释，再说明下一步要补测什么、查框架还是查算子，以及选择它的依据。项目把这次换向和新证据一起保存，下一轮继续读取这段历史。

| 下一步要查什么 | 能区分它的证据 | 证据回来后怎么走 |
| --- | --- | --- |
| 请求是在排队，还是在框架里被拖慢 | 对同一请求记录入队、出队、准备完成、送入设备的时间 | 若时间集中在准备阶段，让 Specialist 查具体调用位置，再提小补丁 |
| 设备计算占了多少，可从哪个算子省下来 | 对齐实际请求和设备 trace，核对热点耗时、调用点及输入形状 | 若热点有足够收益空间，派给算子路线试做，再回到 SGLang 复测 |
| 分块方向还有没有新依据 | 核对已有样本、新工作点或不同输入形状是否支持新的分块假设 | 有新依据才重新探索。否则交付这个方向的试验结果和限制 |

图上把换向画成实际交接。例如 `#46 Coordinator → Orchestration` 携带已试候选、停滞原因和待补的证据，接收方随后给出新的调查方案。下一轮仍从已接受版本出发。

### 人能介入

人发现方向重复，可以在当前会话留一句「暂停分块搜索，先查排队和实际 Prefill 时间」。项目记录原话、接受它的事件和后续动作。暂停时，界面显示正在运行的任务如何收尾和资源是否已归还。恢复时显示从哪个已确认的状态继续。若负责人要换基线、负载或验收门槛，则创建新会话并引用上一轮证据。

### 故障时怎么收尾和继续

遇到可恢复故障，项目按既定规则清理，确认旧进程和资源已释放，再重试未完成的动作。恢复时从磁盘读取最后一次确认的会话状态和已完成回执。日志可以显示「Forge 编译失败，旧进程已清理，最后可用版为 `R03`，准备重试未完成的算子任务」。

遇到无法继续的阻断，项目保存**最后一步、卡住的原因、已完成的结果和恢复入口**，然后结束或进入明确的等待状态。到预算上限时，报告如实标明哪些方向已经验证，哪些只完成了调查，哪些因条件不足未完成。候选能否保留、会话是否结束、最终双目标是否达成，各有对应状态。

## 4. 输出文件与 Markdown 报告样例

每次运行由项目保存这些文件。事后你可以自己读，也可以把会话目录交给另一个 Agent 总结。

| 文件 | 保存什么 |
| --- | --- |
| `console.log` | 运行时显示过的操作、等待、失败、重试和进度，用简明文字说明 |
| `events.jsonl` | 按顺序保存部件的实际交接和执行状态，可按事件编号与日志互查 |
| `evidence/agents/` 与 `evaluation/` | Agent 的输入和回复、实际启动、验证、测速及裁决用的原始证据 |
| `manifest.json`、`report.md` 与交付产物 | 冻结的任务和配置、按模板生成的事实报告、补丁和复现入口 |

项目从已记录的事件和回执生成 `report.md`。文件从已知事实给出本轮结论和证据入口，另请 Agent 解读属于运行后的可选操作。

整份会话目录可以直接交给另一位操作者或 Agent。终端日志保留关键动作和状态变化，每条带事件编号。根据编号可以在报告和事件文件里找到**Agent 提了什么、项目实际做了什么、最后测到了什么**。目录内的引用使用相对路径，并提供原始基线、接受版和复现入口。留在远端的大体积证据注明原始位置和摘要。

下面展示报告节选，证据位置以会话目录为起点。

```markdown
# demo-910b3-01 优化报告

## 结论

- 会话已结束。最终接受版本为 R04，由 R03 的框架补丁和新算子组成。
- 本例同一版本同时达到吞吐 +15% 和 TTFT P95 −15% 的目标。
- 原始基线为分块 512，父版本为 R03。正式测速关闭 Profile。
- 终止原因为三个方向已得到结论，整栈和留出请求复测通过。

## 实测成绩

| 工作点和基准 | 吞吐 | TTFT P95 | TPOT P95 |
| --- | --- | --- | --- |
| 主负载，R04 对原始基线 | 100.00 → 116.00 tok/s（+16.00%） | 200.00 → 168.00 ms（−16.00%） | 15.00 → 15.40 ms（+2.67%） |
| 主负载，R04 对配对父版 R03 | 109.00 → 116.00 tok/s（+6.42%） | 174.00 → 168.00 ms（−3.45%） | 15.20 → 15.40 ms（+1.32%） |
| 留出请求，R04 对对应原版 | 96.00 → 111.36 tok/s（+16.00%） | 210.00 → 176.40 ms（−16.00%） | 15.50 → 15.90 ms（+2.58%） |

主负载与留出请求各四组，均通过逐 token 校验。原版、父版、候选的
启动记录、实际加载文件、各轮样本和清理结果可逐项复核。

## 三个方向的结论

- 调参 R01、R02。分块尝试均未通过单轮收益门槛，保留样本并回退。
- 框架 R03。减少重复输入准备，真实加载并通过配对复测，接受。
- 算子 R04。新算子和 R03 同次加载，正式请求实际命中，整栈复测通过。

  说明假设和验证方式。Router 准入并登记 R01，Dispatcher 随后派发。
  Agent 原始回复见 evidence/agents/turn-017.json。

  Agent 原始回复见 evidence/agents/turn-062.json。
- 10:09 · #65 · Critic → Intent Router。允许试跑，要求覆盖不同输入长度。
  Router 将意见反馈给提案方，并登记集成任务。
  Agent 原始回复见 evidence/agents/turn-065.json。
- 11:25 · #121 · Evaluator → Coordinator。交回 R04 的加载、输出与
  配对计时回执。Coordinator 按独立裁决写回接受版本。

## 产物与复现

- 冻结任务、启动参数与原始基线身份见 manifest.json。
- 可复用的框架和算子补丁、来源及版本摘要见交付清单。
- 整栈配对测量见 evaluation/R04/，留出请求复测见 evaluation/R04-holdout/。
- 完整事件、Agent 原始回复和信号流可从报告中的对应入口打开。
```

完整报告逐条保留实际参与的 Agent 输出及接收方动作，也保留被挡下、失败或回退的提案。若只有部分指标测齐，报告标明证据缺口、是否还能补测，以及对最终验收的影响。每个提升都能追到对应工作点、同一版本的实际加载记录和原始样本。

## 5. 「最新说明」样例

项目提供一份常驻的 `最新说明.md`。它指向当前会话和对应报告，分别显示**正在试的版本**、**最近通过验证的版本**、**整个项目的目标状态**。可以在本次运行结束前查看。

```markdown
# 最新说明

- 更新至 10:47 · demo-910b3-01 · 事件 #94。
- 正在试 R04。已启动整栈复测，正在核对框架补丁和新算子的加载身份。
- 最近通过验证的是 R03。对原始基线吞吐 +9%，TTFT P95 −13%。
- 两个 15% 的目标尚未同时确认。R04 的正式计时和留出请求复测待完成。
- 最近换向。分块尝试未达到单轮门槛，补采调度时序后转查重复输入准备。
- 入口。打开本轮信号流查看 #94，打开 report.md 查看已有结果及补丁、回执入口。
```

项目根据已提交的事件更新最新说明。`R04` 复测成功并写回后，说明才显示它为最近通过验证的版本，并标明双目标达成。若进程中断，说明保留最后一条已确认事件，标明等待清理或可以恢复的状态。历史报告随各自会话保留，用于回看此前尝试。

## 6. 怎样判断这个设计对人有用

- 换一个人接手，他只需准备任务文件和启动配置，再执行一条命令。项目按 `baseline_mode` 准备原始基线和 Reference，创建会话，并在启动摘要展示基线和验收目标。
- 启动后让项目无人值守地运行。成功结束或遇到阻断时，都能从已保存的日志看到最后一个实际动作及原因，并找到对应证据和已完成结果。
- 运行中，他能顺着一个候选查到谁提出、谁接收、谁审查、谁执行、结果怎么写回，也能看到等待或换方向的原因。
- 结束后，将同一份会话目录交给其他人或 Agent，就能从报告查到实际交接、用原始证据复核裁决，并从最新说明找到可以复现的版本。

第一版用同一条命令做两次验收。

1. **正常运行。** 启动后无人值守。结束后只读会话文件，就能逐项核对双指标、正确性、停止原因和最终交付的版本。
2. **运行中遇到可恢复故障。** 在一个允许重试的任务里设置一次受控故障。检查项目能按规则清理、重试和继续，并在同一目录保留失败记录、恢复回执及最终结果。
