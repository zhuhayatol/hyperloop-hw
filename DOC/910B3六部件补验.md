2026-11-24。继续使用 910B3、SGLang 0.5.16、CANN 9.0.0 和固定的 Qwen2.5-0.5B-Instruct。服务实测沿用四组固定请求和独立采集的原版参考输出，按原规则逐 token 校验。恢复实验用预设的分块 768 候选，启动补救用预先给定的最小修复。

## Recovery · 真机进程中断

第一次让编排进程在候选服务就绪、任务回执尚未写入时退出。故障脚本确认遗留服务仍能返回 HTTP 200。正常 `resume` 识别并清理该服务，保留中断记录，派发新的 `task-0003` 重试。

第二次在候选和父版各完成三轮配对计时、已经写入回执时结束编排进程。正常 `resume` 复用这份回执，基线和计时文件的 SHA-256 保持一致，只登记一次裁决。分块 768 的配对吞吐提高 3.16%，低于冻结的 5% 门槛，裁决 `REVERT`。

## SWEEP · 多并发点扫描

恢复会话自动派发了并发 1、2、4 的扫描。由于本轮 768 被退回，原版和保留版均为分块 512。三个并发点各启动两个独立服务，每侧完成四组逐 token 校验和三轮计时。扫描写回 `all_pairs_complete` 后，Coordinator 进入第二轮。第二轮无新的已验收版本，扫描以 `no_validated_change_since_sweep` 跳过，会话按两轮上限结束。

该测试在运行前锁定两轮上限，并把整体提前收尾目标设为 100%，用于覆盖进入下一轮的分支。候选的 5% 接受门槛沿用原规则。

[自动扫描证据](../.runs/910b3-six/sweep-recovery/real/sweep-recovery/evidence/sweep/task-0004.json)

另一次独立调用真实 SWEEP 动作，先核对历史 768 版的 KEEP 裁决和测量摘要，再在并发 1、4 重新测量 512 和 768。启动回执分别确认分块，四次服务启动各通过四组逐 token 校验和三轮计时。两版本扫描单独留档，原会话的裁决照常保留。

| 并发 | 512 吞吐 | 768 吞吐 | 512 首 token P95 | 768 首 token P95 |
| --- | ---: | ---: | ---: | ---: |
| 1 | 62.45 tok/s | 63.99 tok/s | 130.51 ms | 73.96 ms |
| 4 | 136.90 tok/s | 29.67 tok/s | 286.39 ms | 2824.44 ms |

表中为三轮中位数。并发 4 的两侧都有明显波动。512 三轮吞吐为 136.90、28.28、148.75 tok/s，768 为 29.67、28.89、166.10 tok/s。这组数据用于验证扫描能发现差异并保存原始波动，稳定性能结论还需更多复测条件。

## Enablement · 启动失败补救

把原版启动参数从分块 512 改成 513，页大小仍为 128。真实 SGLang 进程触发 `chunked_prefill_size must be divisible by page_size`，启动失败并保存退出回执。Coordinator 进入 Enablement，采用事先冻结的最小修复改回 512。

补救进程就绪后，执行端从 `/server_info` 核实实际分块为 512。四组输出与独立原版参考逐 token 一致，三轮实测的吞吐中位数为 103.95 tok/s，首 token 延迟 P95 的中位数为 187.15 ms。Coordinator 登记可运行基线并收尾。该试验证明了真实失败后的补救流程，自动生成修复提案另待验证。

## Kernel Agent、GEAK 和 Forge

Kernel Agent 读入此前 910B3 真机 Profile，并核对原始报告的 SHA-256。该 Profile 把 `SwiGlu` 关联到 SGLang 的 `sglang/srt/layers/activation.py:123`。直接调用真实路由任务，分别生成 GEAK 的 `service_candidate` 请求和 Forge 的 `operator_patch` 请求。执行端缺少昇腾原生工具适配，两条都停在派发前，结果为 `native_kernel_driver_unconfigured`。

| 部件 | 在 910B3 上实际执行的检查 | 结果 |
| --- | --- | --- |
| Kernel Agent | 核对真机 trace 和父版本，生成两种有明确交付类型的请求 | 交接通过，真实工具派发受阻 |
| GEAK | 运行上游原版设备探针 | 缺少 ROCm 的 `rocminfo`，探针退出码为 2 |
| KernelForge | 运行上游 `detect_arch()` | 无法识别 AMD `gfx` 设备，架构返回空值 |

真实路由在 `3f9e663` 起会保留交接证据并给出阻断结果。模拟路线继续按原有规则运行。

## 独立 SwiGLU 真机实验

用真机 Profile 定位到的 SwiGLU 作为实验对象，按模型宽度构造两种代表性 BF16 输入。Triton-Ascend 实际生成了 910B3 的 `npubin`。现有算子和新候选均与独立 CPU 参考一致，两种形状的最大绝对误差都为 0。每种形状预热 10 次，两侧交替用 NPU stream event 记录 25 个样本。

| 输入形状 | 现有 Torch NPU SwiGLU 中位数 | 新 Triton-Ascend 候选中位数 |
| --- | ---: | ---: |
| 2 × 9728 | 196.50 μs | 300.70 μs |
| 512 × 9728 | 233.46 μs | 336.48 μs |

这个实验验证了昇腾上的编译、执行、独立校验和计时。两种形状的候选都更慢。这份候选的 SGLang 加载和 GEAK／Forge 交付仍待验证。
